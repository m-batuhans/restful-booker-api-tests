# Restful-Booker API Tests: AI-generated test cases, human-reviewed

[![Tests](https://github.com/m-batuhans/restful-booker-api-tests/actions/workflows/tests.yml/badge.svg)](https://github.com/m-batuhans/restful-booker-api-tests/actions/workflows/tests.yml)

API test automation for [Restful-Booker](https://restful-booker.herokuapp.com), a practice API with intentional bugs.

The point of this project is not only the tests. An LLM designs the test cases from the API documentation, a human tester reviews every case against the documentation, and only the reviewed cases are automated. Every step leaves a file in this repository, so each decision can be traced.

## How it works

```
0. Fetch documentation   tools/fetch_api_docs.py    → api-docs/restful-booker.md
1. Generate test cases   tools/generate_cases.py    → docs/01-ai-generated-cases.md
2. Review                human                      → docs/02-review.md
3. Implement             test code                  → src/test/java/restfulbooker/
4. Run                   mvn test
5. Report                human                      → docs/03-bug-reports.md
```

**0. Fetch documentation.** The documentation page renders its content with JavaScript. The script reads the underlying apiDoc JSON (`/apidoc/api_data.json`) and converts it to Markdown word for word, including every example tab.

**1. Generate test cases.** The script sends a fixed prompt ([`prompts/generate-cases.md`](prompts/generate-cases.md)) and the documentation to the Gemini API. The raw output is saved unchanged, with the model name and date in its header, and is never edited afterwards. The script refuses to overwrite an existing output, so the review always matches what the AI actually produced.

**2. Review.** Every AI-generated case gets a decision (keep, fix, drop), a reason and a final expected result. The documentation defines no error responses at all, so the review starts with explicit rules for deciding an expected result when the documentation is silent or contradicts itself (in testing terms: an oracle policy). The review also checks the AI's list of documentation problems against the documentation itself.

What the review changed most often:
- **Weak assertions.** A 200 response does not prove an update was saved, so updates and deletes are verified with a follow-up GET.
- **Missing boundaries.** The date filters are documented as "greater than or equal", but the AI never tested the "equal" case or the excluded side. These boundary tests later found BUG-06.
- **Misread documentation.** The AI treated headers labelled "Optional: no" as mandatory. apiDoc adds that label automatically, and the documentation's own example omits the header.
- **Fields tested only in isolation.** The AI never tested relations between fields, such as a checkout date before the checkin date.

**3. Implement.** One test method per case. The case ID is in `@Tag` and `@DisplayName`, so every test links back to its review decision and can be run on its own. Tests create their own data and never rely on existing records.

**4. Run.** Tests run against the public instance, locally and on every push through GitHub Actions ([`.github/workflows/tests.yml`](https://github.com/m-batuhans/restful-booker-api-tests/blob/main/.github/workflows/tests.yml)). Steps 0 and 1 are not part of CI: they are run by hand, because a new generation produces different cases and would invalidate the review.

**5. Report.** Not every failure was an API bug. Each one was classified as a test-code error, a documentation problem or an API bug. Test-code errors were fixed. API bugs are written up in `docs/03-bug-reports.md`, tracked as GitHub issues, and the affected tests are marked `@Disabled("Known bug: BUG-XX, see docs/03-bug-reports.md")`. They are skipped, not deleted, and their assertions are unchanged, so the suite stays green and any new failure stands out.

## How AI was used

AI is part of this project's pipeline, so how it was used is part of the project.

| Step | AI | Me |
|---|---|---|
| Test case generation | Gemini API, through `tools/generate_cases.py` | Decided that generation had to be a script with an API key instead of a manual chat step; wrote the prompt with Claude; ran the generation |
| Documentation source | — | Found that the first documentation copy had lost the content of every example tab, which invalidated the first review; required fetching to be a script and had the whole chain re-run |
| Review | Drafted in discussion with Claude (chat) | Every decision and the final content are mine. I read and revised the rules and the decisions, and pushed back on reasoning I did not find defensible, which changed several expected results |
| Scripts and test code | Claude Code, under the rules in [`CLAUDE.md`](CLAUDE.md) | Approved those rules, reviewed every change, ran every test myself |
| Failure analysis and bug reports | Failures classified in discussion with Claude (chat); written up by Claude Code from real test logs | Confirmed each classification, and decided that no failing test would be made green by weakening an assertion |

`CLAUDE.md` holds the rules Claude Code works under. The most important one: never change an expected result to make a test pass, because in this API a failing test may be a real bug.

## Problems solved along the way

- **Incomplete documentation.** The first copy of the documentation was made by copy and paste, which lost the content of every tab. This surfaced when an XML test failed for the wrong reason. Fetching was turned into a script, and the chain was run again from step 1.
- **A hidden request header.** REST Assured appends a charset to `Content-Type`. With it, the XML request returned 500; the same request sent with curl without the charset returned 200. XML and URL-encoded tests now send exactly the documented headers.
- **Exceptions instead of assertions.** For every method except POST, REST Assured's internal HTTP client threw an exception on non-2xx responses before any assertion ran. A small helper (`support/HttpCalls.java`) returns the status code instead, so negative tests reach their assertions.
- **Stale test data on a shared server.** An early exploration of BUG-06 pointed at the wrong defect, because the public instance had reset itself and the booking under test no longer existed. The exploration was repeated and the booking was confirmed to still exist after the last query before the conclusion was written.

## Running the project

**Requirements:** Java 17, Maven. Python 3 only for regenerating the documentation and test cases.

**Configuration:** copy `src/test/resources/config.properties.example` to `src/test/resources/config.properties` (gitignored) and fill in `base.url`, `auth.username` and `auth.password`. The public values are in the API documentation. Environment variables `BASE_URL`, `AUTH_USERNAME` and `AUTH_PASSWORD` are checked first.

```
mvn clean test                      # all tests
mvn test -Dtest=CreateBookingTest   # one test class
mvn test -Dgroups=TC-CREATE-001     # one case
mvn test -Dgroups=SMOKE             # smoke test
```

**Regenerating the documentation and test cases:**

```
pip install -r requirements.txt
python tools/fetch_api_docs.py
python tools/generate_cases.py
```

`generate_cases.py` needs a Gemini API key. Create one in [Google AI Studio](https://aistudio.google.com/apikey) and set it as an environment variable:

```
setx GEMINI_API_KEY "your-key"      # Windows, then reopen the terminal
export GEMINI_API_KEY="your-key"    # macOS and Linux
```

The key is only read from the environment and is never stored in the repository. The model defaults to `gemini-3.6-flash` and can be changed with `GEMINI_MODEL` (useful when a model is busy and the API answers with 503).

The script does not overwrite `docs/01-ai-generated-cases.md`; remove the old file first. A new generation produces different cases, so the review has to be redone.

## Known limitations

- **Shared server.** The public instance is used by others and resets itself periodically. A test can occasionally fail for this reason; a re-run confirms it, and test data should be verified to still exist before a filter result is interpreted.
- **apiDoc-specific fetcher.** `fetch_api_docs.py` reads apiDoc's JSON format and would need a new reader for other documentation formats.
- **Non-deterministic generation.** The generator is run manually, not automatically, because each run produces a different set of cases.
- **CI runs against the shared instance.** A red CI run is not always a code problem; the surefire reports are uploaded as an artifact on every run so a failure can be checked.
