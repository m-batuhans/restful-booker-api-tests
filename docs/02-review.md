## Oracle policy
How the expected result of a test is decided, in this order:

1. **The documentation states it.** Then that is the expected result.
2. **The documentation disagrees with itself.** The documentation is generated by apiDoc, which writes some labels automatically: every success section is titled "Success 200", and every field not explicitly marked optional is shown as "Optional: no". Text and examples the author wrote by hand win over these automatic labels. If two hand-written parts disagree, the detail is not used as an expected result and is logged as a finding.
3. **The documentation is silent, but HTTP rules are clear.** A resource that does not exist → 404 Not Found. Invalid input (missing required field, wrong format, invalid value) → 400 Bad Request. Missing or invalid credentials on a protected endpoint → 401 Unauthorized or 403 Forbidden (both accepted, because the documentation does not choose). A response body in XML → a Content-Type header that says XML.
4. **The documentation is silent and HTTP rules do not decide.** The test checks only what must be true in any case (for example: no token was issued, the booking was not changed), and logs the actual status code.

Rules applied to every test (not counted as changes):
- A precondition like "booking exists" means the test creates that booking itself. Tests never rely on existing data.
- Names used in filter tests get a unique suffix, so other users of the shared server cannot affect the result.
- A request body field is required unless it is marked optional or the documentation's own examples leave it out.
- A booking ID that is guaranteed not to exist is obtained by creating a booking and deleting it. If the deletion fails, the test stops with an error instead of giving a false result.
- XML and URL-encoded requests use exactly the headers shown in the documented example.
